# Work log

What was done on Mixcloud Direct and why, in order, plus what's still open.
How things work (APIs, LMS internals, gotchas) lives in `../CLAUDE.md`. Read that first.

## Picking this up again

1. Read `CLAUDE.md` (technical notes) and the **Open threads** section below.
2. `../KEXP/scripts/installs.sh` (in the sibling KEXP repo) shows install counts for both
   plugins and whether the official Mixcloud plugin has taken our fix (PR #51).
3. `python3 scripts/smoke.py` checks that Mixcloud still behaves as the plugin assumes.
4. `prove tests/`, then `scripts/dev-server.sh` + `scripts/test-player.sh` to try things on LMS 9.0.0.
5. Release: bump `<version>` in `src/MixcloudDirect/install.xml`, commit, `scripts/release.sh`.

## Why this exists

The owner's Lyrion server runs **LMS 9.0.0** (RPM, Red Hat, Perl 5.28) and **can't be upgraded**
(hardware). In Nov 2026 the official Mixcloud plugin (danielvijge/lms_mixcloud) stopped working there:

- **Login:** Mixcloud's OAuth endpoint replies `Content-Encoding: identity`, and LMS before 9.2
  inflates it into garbage (fixed in LMS 9.2, slimserver af0afcb; upstream issue #46). The
  plugin then re-sent the one-time code and got `400 bad_verification_code` over and over.
- **Playback:** it shells out to yt-dlp (and ffmpeg for HLS), which that server didn't have.
- Also found along the way: Mixcloud answers HTTP/1.0 (LMS's default) with `426`, and its audio
  CDN returns `403` for LMS's default `iTunes/…` User-Agent.

Upgrading LMS wasn't an option, so we built a separate plugin that needs neither login nor helpers.

  bare text fields. New layout: four top-level links with distinct `MTL_icon_<name>` icons,

  - README, description and settings now say plainly who it's for (servers that can't upgrade)

  - Tested on LMS 8.5.2, 9.0.0, 9.1.2 and 9.2.0.
  - KEXP-style repo extras: `installs.sh`, settings links, disclaimer, GitHub topics.

## Decisions and why

- **Read-only, no OAuth.** It avoids the LMS < 9.2 login bug entirely, and matches the upstream
  maintainer's own direction: he removed follow/favourite because "those actions should be done
  from the Mixcloud website". The owner chose "simple and dependable" over write features. Keep
  it read-only; the README, description and settings page all say so.
- **Our own HLS/fMP4 player in Perl** instead of yt-dlp/ffmpeg: no binaries, about 1 ms of CPU
  per 10 s of audio, accurate seeking.
- **Separate identity:** plugin id `MixcloudDirect`, prefs `plugin.mixclouddirect`, scheme
  `mcdirect://`. It never collides with the official plugin (`MixCloud`, `plugin.mixcloud`,
  `mixcloud://`), so both can be installed together, and the owner keeps both to track upstream.
- **Follows are local**, by design, and clearly labelled "Follow in Lyrion".
- **Version claims** in docs name exactly what was tested (8.5.2, 9.0.0, 9.1.2, 9.2.0).
- **Docs and repo are public**: keep the owner's private details (server address, accounts) out.

## Open threads

- **PR #51**: waiting for danielvijge. If he wants the single-use-code fix, add a commit that
  keeps the access token in prefs and only exchanges the code when there's none (or it's rejected).
  `installs.sh` shows when a release includes the fix. The owner's server has the 0.13.0.51 test
  build and switches automatically to any official release above it (0.14+).
- **Official plugin list**: after a week or two of outside feedback, submit `repo.xml` via a PR to
  [LMS-Community/lms-plugin-repository](https://github.com/LMS-Community/lms-plugin-repository).
  Expect questions about why not upstream (answer: PR #51, plus servers without yt-dlp/ffmpeg)
  and stream-url decoding (streams for listening only, as yt-dlp does).
- **Not done / ideas:**
  - Live streams have no track titles (Mixcloud doesn't publish any).
  - Video-only live streams aren't supported (all seen so far have an audio rendition).
  - Only Linux Docker and the owner's Red Hat server have been tested, not Windows or macOS LMS.
  - Mixcloud Select (subscriber-only) shows can't play and are hidden by default.
